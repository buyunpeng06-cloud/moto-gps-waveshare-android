## Phase 1 status — BLE connection and protocol self-check

### Implemented in this subtree

- Kotlin + Jetpack Compose Android app scaffold; UI, ViewModel and BLE repository are separate.
- Scan filtering by the actual upstream Navigation Service UUID; explicit device selection before connecting.
- Uses the upstream service/RX/TX UUIDs, discovers GATT services, requests MTU 247, enables TX Notify, and relies on Android's bonding/security flow when the firmware requires encrypted GATT access.
- BLE v1 frame encoder/decoder: little-endian header fields, CRC-16/CCITT-FALSE, message fragmentation bounded by the negotiated MTU-derived characteristic value size, and contiguous reassembly.
- Two-step Device Ready handshake: Phone Starting → Device Ready → Phone Ready → final Device Ready. Business data is not sent before the final Ready.
- GATT characteristic writes are serialized; fragments of one logical message are enqueued as a unit. Disconnect clears pending writes and handshake state.
- Heartbeat uses elapsed time since the current application session began, not the phone's boot time.
- Phase 1 advertises zero business capabilities in the handshake until navigation/map/media payload producers and consumers are implemented; this avoids claiming unsupported features.
- Exact upstream golden byte fixtures are copied into `app/src/test/resources/ble-navigation-v1.golden.txt` with source attribution.
- JNI adapter in `app/src/main/cpp/` delegates BLE CRC/frame encoding/decoding/fragmentation to the existing `shared/ble_protocol` C++ implementation. Host CMake + JNI golden self-test passes.

### Not implemented yet

- Real navigation, location provider, route search/preview, route refresh/deviation, map download/storage and media controls.
- App ACK/retry for DeviceCommand, full command de-duplication and robust retransmission policy; these are required before sending/acting on business commands and are not claimed complete by this BLE handshake alpha.
- Navigation foreground service and lock-screen validation. This phase does not start location tracking.
- Gradle Wrapper JAR/scripts. The container has JDK 21 and kotlinc but no Gradle, Android SDK, or wrapper JAR; external network resolution is unavailable here. Do not treat the Android app build as passed until run with the wrapper generated by a working Gradle installation in the full upstream checkout.

## Build and test

From `platforms/android/` in a full Android development environment:

```bash
# After the official Gradle Wrapper files have been generated and committed:
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug
```

The current sandbox did not have Android SDK or Gradle installed, so those Android tasks have **not** been executed here. The protocol golden self-test passed both the Kotlin reference path (`tools/run-protocol-selftest.sh`) and the host-compiled JNI/shared-C++ path (`tools/run-jni-host-selftest.sh`). The Android Gradle/APK tasks still have not run.

Install only after a successful Android build:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

On Samsung S25, grant **Nearby devices** when prompted and turn on Bluetooth. Scan for the MOTO GPS service, explicitly select the correct board, and accept the Android pairing prompt if the firmware requests bonding. If service discovery fails, verify the exact `1.75C` model and firmware version; this app deliberately does not weaken firmware encryption.

## Permissions and limitations

- `BLUETOOTH_SCAN` and `BLUETOOTH_CONNECT` are runtime permissions on Android 12+.
- Location permissions are declared separately for the planned navigation stage; this phase does not request or collect location.
- The scan permission uses `neverForLocation` because BLE scan results are not used to infer location. This does not remove navigation location permissions.
- Android may restrict background work depending on OS version, battery settings and manufacturer policy. Lock-screen reliability has not been tested on the Samsung S25.
- No gateway is bundled. The upstream backend uses `GET /v1/places`, `POST /v1/route-options`, `POST /v1/routes`, and map endpoints under the configured base URL; real navigation requires the user's own reachable HTTPS gateway and server-side AMap Web Service key. The Web Service key must never be embedded in the APK.
- No fake route or location fallback is used.

## Upstream protocol facts verified from source

- Service UUID: `7e57a000-b50c-4b6a-9c57-40a54e8e1000`
- Phone → device RX: `7e57a001-b50c-4b6a-9c57-40a54e8e1000` (encrypted writes)
- Device → phone TX: `7e57a002-b50c-4b6a-9c57-40a54e8e1000` (encrypted notifications)
- Each frame includes a 10-byte header and 2-byte CRC; max characteristic value is `min(ATT_MTU - 3, peer max_frame_size, 512)`.
- Connection handshake is not complete until the second Device Ready agrees with the first Device Ready.
